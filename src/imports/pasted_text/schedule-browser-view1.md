Corresponding Update to the Master Prompt — Part 3, View 1
The Schedule Browser section of Part 3 currently describes only a list-based slot display. Replace or extend the View 1 specification with the following complete redefinition:

View 1 — Schedule Browser with Real-Time Availability Calendar.
This view is the primary entry point for visitor scheduling discovery and must be laid out as a two-panel horizontal composition on desktop: the left panel occupies approximately 55% of the container width and displays the time slot listing; the right panel occupies the remaining 45% and displays the interactive availability calendar. On tablet devices, the calendar shifts to sit above the time slot listing (stacked vertically, calendar on top). On mobile devices, the calendar renders first as a full-width compact component, and the slot listing scrolls below it. This layout directly satisfies the responsive requirement for mobile users and the spatial relationship described in FR-GP-11.
The Right Panel — Real-Time Availability Calendar. The calendar is a month-view grid, displaying all days of the current month by default, with navigation arrows to advance or retreat one month at a time. Every single date cell must reflect a live, on-demand query of the database — never a cached or statically stored state — to determine which of the three availability states applies to that date.
The three date states are defined as follows and must be visually distinct from one another with no ambiguity: a Fully Available date means at least one time slot on that day has open capacity; a Partially Available date means at least one slot is open but at least one other slot on the same day is fully booked; and a Fully Booked date means every time slot on that day has reached its capacity limit and no new bookings can be accepted.
Each state must receive a unique visual treatment. Use a solid teal fill (#0f766e) with white text for Fully Available dates, because teal is already established in the portal's color language as the indicator of availability and open status — this is directly consistent with how the "Open daily" and "Over 2,000 items" status badges are styled across the main portal. Use an amber fill (rgba(245,158,11,0.15)) with #92400e text for Partially Available dates, providing a cautionary middle state. Use a muted gray fill (#f1f5f9) with #94a3b8 text and a subtle strikethrough or diagonal line overlay for Fully Booked dates, so they read as disabled without being harsh or alarming. Dates in the past must appear in the same disabled state as Fully Booked dates and must be unclickable. Today's date must carry an additional thin 2px ring border in #334155 to anchor the visitor's current position in time.
A legend must appear directly below the calendar grid, using three small colored squares (12×12px, border-radius: 3px) followed by their labels in Inter:Regular, weight 400, approximately 12px, color #64748b. The three legend items are: "Available" (teal square), "Limited" (amber square), and "Unavailable" (gray square). This legend must always be visible — never hidden behind a tooltip or dropdown.
When a visitor clicks a Fully Available or Partially Available date on the calendar, two things happen simultaneously: the left panel's time slot listing filters to show only the slots for that selected date, and the selected date cell receives a 2px solid #334155 border to confirm selection. This interaction is the primary navigation mechanism between the calendar and the slot listing — the calendar drives the left panel, not the other way around. Clicking a Fully Booked or past date produces no navigation action; instead, display a brief inline message directly below the calendar: "No slots are available on this date. Please select another date." styled in Inter:Regular, weight 400, #64748b, 13px.
The calendar heading (month and year, e.g., "May 2026") must be rendered in Inter:Semi_Bold, weight 600, approximately 17px, color #1e293b, centered above the grid. Day-of-week column headers ("Su", "Mo", "Tu", "We", "Th", "Fr", "Sa") must use Inter:Semi_Bold, weight 600, approximately 12px, color #64748b. Date numbers within cells use Inter:Semi_Bold, weight 600, 14px, with color adapting to whichever state fill is behind them (white on teal, dark on amber, muted on gray). Navigation arrows (chevron left and right) use the secondary button style — no fill, #e2e8f0 border, #1e293b icon color, 32×32px touch target for mobile compliance.
On mobile specifically, the calendar's month grid must reduce cell padding to keep all 7 columns visible without horizontal scrolling. The minimum touch target per date cell is 40×40px to satisfy mobile usability requirements (NFR Usability). The font size of date numbers may reduce to 12px on mobile to accommodate the compressed grid, but the color-coded availability states must remain fully intact — the visual communication must not be sacrificed for the sake of compactness.
The Left Panel — Time Slot Listing. This panel displays a vertical list of time slot cards for the currently selected date (or today's date by default). Each card shows: the gallery name, start and end time, a real-time remaining capacity indicator (e.g., "8 of 20 spots remaining"), the group types accepted for that slot, and a "Select This Slot" button in the primary button style (#334155 background, white text). When remaining capacity drops below 20% of total capacity, replace the normal capacity text with a teal badge reading "Almost Full" using the status badge style (#0f766e, rgba(15,118,110,0.1) background). When a slot is fully booked, replace the "Select This Slot" button with a disabled gray button labeled "Fully Booked" and remove it from keyboard tab order so keyboard-only users are not forced to navigate through unactionable elements.
The left panel must always maintain visual synchronization with the calendar — the date shown in the slot listing header must always match the date selected in the calendar, displayed as a clearly readable formatted date (e.g., "Wednesday, May 7, 2026") in Inter:Semi_Bold, weight 600, approximately 16px, color #1e293b, at the top of the left panel. This header date acts as a persistent orientation anchor so the visitor always knows which day's slots they are viewing, which directly satisfies the usability non-functional requirement that all critical workflows be completable with minimal confusion and within a minimal number of steps.

Double-Check Pass Against All Existing Requirements
Now, here is the honest verification of what was already in the prompt and what warranted correction or reinforcement in light of this addition.
The existing FR-GP-3 (automatic validation for conflicts, capacity limits, and required field completeness) remains intact and complementary — the calendar now provides pre-submission awareness of capacity, so when the user reaches the booking form, FR-GP-3's validation is a confirmation of something they already had visual context for, not a surprise rejection.
The existing NFR Performance requirement that figures be derived from on-demand database queries and never from redundant stored values now applies explicitly to the calendar's date states. This must be called out to the implementation agent — the calendar must not cache availability states locally for more than a reasonable debounce interval (recommended: re-query on each month navigation and on each page load, with a 30-second soft cache maximum to prevent database flooding during peak public access periods).
The existing NFR Usability statement that "all critical workflows are completable within a minimal number of steps" is now much better served — previously, the visitor had to scroll through a potentially long undifferentiated list of time slots to find an available date. The calendar reduces that to a single glance and a single click to filter.
The existing NFR Scalability requirement that the notification dispatch and public interface handle growing concurrent users without degradation now has an additional implication: the calendar's real-time queries must be optimized (indexed date and capacity columns in the database) so that concurrent calendar loads during peak periods — such as school enrollment season — do not degrade response times.
