PREAMBLE: HOW TO READ AND USE THIS PROMPT
This prompt is a binding specification document. Every instruction here is derived directly from either the Software Requirements Specification (SRS) or the Typography System Documentation for the Naga City Historical Museums portal. You must treat every section as a constraint, not a suggestion. Before writing a single line of code, read this entire document. When in doubt between two implementation choices, always default to the one that more closely satisfies a stated functional or non-functional requirement.
This module serves three distinct stakeholders: the General Public (visitor-facing scheduling interface), Museum Staff (operational back-end interface), and Curators (oversight and management interface). Each stakeholder has an isolated role, a defined set of functions they may access, and a distinct visual context. You must never expose one stakeholder's functions to another.

PART 1 — DESIGN SYSTEM & TYPOGRAPHY (NON-NEGOTIABLE CONSTRAINTS)
This section defines every visual rule. Deviation from these rules constitutes a non-functional requirement violation.
Font Families. The system uses two fonts in layered operation. The global fallback font is 'Roboto', sans-serif, loaded from Google Fonts at weights 400, 500, and 700. It is declared on the * and body selectors in globals.css. The primary display and component font is Inter, referenced in component-level Tailwind classes using the Figma convention font-['Inter:Weight_Name',sans-serif]. Inter must be loaded at weights 300 (Light), 400 (Regular), 600 (Semi Bold), and 700 (Bold). If Inter is unavailable, Roboto serves as the visual fallback. Do not use any other font family anywhere in this module.
Base Font Size. The root html element is set to font-size: 16px via the CSS variable --font-size: 16px. All rem values in the system derive from this base.

PART 2 — ARCHITECTURE & NON-FUNCTIONAL REQUIREMENTS
Architectural Pattern. The system must be built on a layered, service-oriented architecture with five independently maintainable service components: (1) Booking Service, (2) Attendance/Logbook Service, (3) Staff Assignment Service, (4) Schedule Management Service, and (5) Notification Dispatch Service. These must never be entangled — each must communicate through well-defined interfaces or API contracts. The public-facing scheduling interface must be implemented as an isolated front-end component that calls the Booking Service through API contracts, so the visitor UI can be redesigned without touching any operational logic.
Role-Based Access Control (RBAC). Three roles exist: GENERAL_PUBLIC, MUSEUM_STAFF, and CURATOR. Every page, route, component, and API endpoint must enforce this. General public users access zero operational data. Staff cannot access curator-only functions such as role permission management or performance metric tracking. Curators have access to all functions. All access changes must be logged with the responsible curator's identity, the affected user, the change detail, and a timestamp.
Authentication. Staff and Curator users must authenticate before accessing any operational interface. Sessions must auto-terminate after a defined inactivity period (recommended: 30 minutes). The public-facing interface requires no authentication for browsing and schedule viewing, but a valid email address is required for booking submission.
Data Security. All sensitive visitor data — including names, contact numbers, email addresses, and booking records — must be encrypted both in transit (HTTPS/TLS) and at rest. All public-facing form inputs must be validated and sanitized against SQL injection and malformed input before any database operation. Collect only the minimum personal information required to fulfill a booking.
Performance Targets (Hard Requirements, Not Guidelines).
The visitor scheduling interface and the staff dashboard must load within 3 seconds under normal operating conditions. Booking submission, conflict detection, and confirmation generation must complete within 5 seconds. Daily visitor reports and attendance summaries must generate within 10 seconds. CSV and PDF export files must generate within 15 seconds. Booking confirmation emails must be dispatched within 30 seconds of a successful booking submission. Current visitor counts and attendance summaries must be derived from on-demand optimized database queries — never from stored redundant values.
Responsiveness. The public-facing interface must be fully functional on mobile devices (smartphones), in addition to the desktop and tablet support that applies to all stakeholders. Staff and curator interfaces must function correctly on desktop workstations and tablet devices. The system must function across Windows, macOS, and browser-enabled tablet operating systems without any platform-specific dependencies. No proprietary plugins or installation required — web-browser-only deployment.
Conflict Detection. The system must automatically detect scheduling conflicts before any conflicting record is ever written to the database. This includes overlapping visitor bookings, double-assigned staff, and capacity limit violations. This detection must run at the moment of booking submission, schedule approval, and staff assignment — not after the fact.
Transactional Integrity. All multi-step operations — such as booking creation (which involves availability check, record creation, and confirmation dispatch) — must follow an all-or-nothing commit model. If any step fails, the entire transaction rolls back and no partial data is saved.
Graceful Degradation. If a non-critical component (e.g., notification dispatch, export generator) is temporarily unavailable, the core operational functions — booking management, logbook entry, attendance tracking — must remain fully operational. An informative, user-friendly message must appear when any component is unavailable, including an estimated restoration time where possible.
Naming Conventions. All variables, component names, service class names, database table names, and API endpoints must follow consistent naming aligned with the system's data dictionary and ERD. No abbreviations that are not defined in the data dictionary. No inconsistent casing between layers.

PART 3 — GENERAL PUBLIC INTERFACE (Visitor Scheduling Front-End)
This is the public-facing, zero-authentication section of the module. It is the primary entry point for all visitors booking a museum visit.
Page Structure. The visitor scheduling interface consists of the following distinct views, all accessible without login: (1) Schedule Browser, (2) Booking Form, (3) Booking Confirmation Page, (4) Booking Lookup Page, (5) Booking Modification / Cancellation Page, and (6) FAQ / Help Page. These are the exact six functional areas required by General Public functional requirements 1 through 10.
View 1 — Schedule Browser. Display all available visit time slots across the museum's galleries with the following required data points per slot: gallery name, available date, start time, end time, and real-time remaining capacity. This view must be accessible without registration of any kind (FR-GP-1). Capacity must reflect live database state — never a cached or stored redundant value (aligned with NFR Performance). Display a clear visual indicator when a slot is nearly full (e.g., fewer than 5 spots remaining) and a distinct indicator when it is fully booked (slot becomes unselectable). Use the teal badge style #0f766e / rgba(15,118,110,0.1) for available slots and a muted or disabled state for full slots.
View 2 — Booking Form. When a visitor selects a time slot from the Schedule Browser, they are taken to the Booking Form. This form must collect exactly the following fields, no more (data minimization — NFR Security): Full Name (required), Email Address (required, validated format), Contact Number (required), Group Size (required, numeric, minimum 1), Visit Date (pre-filled from selected slot, required), Time Slot (pre-filled from selected slot, required), Group Type — dropdown with options: Individual, School Group, Senior Group, Private Tour (required), and Special Requirements — an optional free-text field where visitors may indicate accessibility needs or other needs (FR-GP-9).
Before the form fields appear, display a clear, accessible privacy notice (FR-GP-10 and NFR Security) stating how the visitor's data is used, stored, and protected. This notice must be visible above the submit button, not hidden behind a link.
On submission, the system must perform these validations client-side first, then server-side before any write: all required fields are populated, email is valid format, group size does not exceed the remaining capacity of the selected slot, the selected slot has no existing conflict, and all text inputs are sanitized against injection. If validation fails, display a clear, descriptive error message at the exact field that failed — not a generic top-of-form error (NFR Usability). The form must be completable in a minimal number of steps (NFR Usability). Display a confirmation feedback toast or overlay immediately upon successful submission (NFR Usability).
View 3 — Booking Confirmation Page. After successful booking submission, display a confirmation page (not just a toast) showing: the generated booking reference number, visitor name, visit date and time, group size, group type, special requirements (if any), and the email address to which the confirmation was sent. Include a printed-card-style summary the visitor can screenshot. The system must also deliver this same information to the visitor's email within 30 seconds (FR-GP-4). Style the reference number in the --text-3xl scale (36px), weight 700, color #1e293b, so it is immediately scannable.
View 4 — Booking Lookup Page. Provide a publicly accessible lookup form where a visitor enters either their booking reference number or their registered email address to retrieve their booking details (FR-GP-5). Display all booking details in the same card layout as the confirmation page. If no matching record is found, display a specific error message: "No booking found for the provided reference or email address." Do not reveal whether an email exists in the system if no booking is linked (privacy protection).
View 5 — Modification and Cancellation Page. From the Booking Lookup Page, once a booking is displayed, offer two action buttons: "Modify Booking" and "Cancel Booking." Both must be disabled and replaced with an explanatory message if the booking falls outside the system-defined cancellation window (FR-GP-6). On cancellation, display a confirmation dialog before executing. On modification, allow changes to: group size, visit date/time (subject to real-time capacity check), group type, and special requirements. Name and contact information may not be modified without staff intervention. After any modification or cancellation, the system must send an automatic status notification email to the visitor (FR-GP-7).
View 6 — FAQ and Help Section. Provide a publicly accessible, always-visible FAQ section within the scheduling interface (FR-GP-10). It must cover at minimum: step-by-step booking instructions, the cancellation and modification policy (including the cancellation window), what to bring on visit day, accessibility accommodation information, and museum visit guidelines. Use an accordion or expandable card pattern for readability. Style headings using Inter:Semi_Bold, weight 600, #1e293b. Style body answers using Inter:Regular, weight 400, #64748b, line-height: 22.75px.
Status Notification System. The system must send email notifications to visitors for the following events without any manual trigger: booking confirmed, booking rejected, booking modified by staff or curator, and booking cancelled (FR-GP-7 and FR-GP-6). Every email must include the reference number, the change details, and a link back to the Booking Lookup Page.

PART 4 — MUSEUM STAFF INTERFACE (Operational Back-End)
Staff users access this interface after authenticated login. The interface must be optimized for daily use on desktop workstations and tablet devices and must load within 3 seconds.
Staff Dashboard (Home View). Upon login, staff see a dashboard that summarizes: today's total bookings, current on-site visitor count by gallery, staff assignments for the day, and any anomalies or missing data highlighted prominently (FR-S-10). Use frosted-glass stat cards — background rgba(255,255,255,0.1), backdrop-blur(6px) — for the four key figures: Total Bookings Today, On-Site Visitors, Pending Logbook Entries, and Active Staff Assignments. Each stat card uses .stat-card-value for the number and .stat-card-label for the label. If any value is anomalous (e.g., logbook entries missing for an arrived group), highlight the stat card with a #AC0000 left border and a warning badge.
Booking Management View. Staff can view, create, and modify bookings for both individual and group visits (FR-S-1). The view displays a table of all bookings (today's by default) with columns: Reference Number, Visitor Name, Group Type, Group Size, Visit Date, Time Slot, Status, and Actions. The Actions column contains "View," "Edit," and "Log Arrival" buttons styled as secondary buttons. Provide a filter bar at the top allowing filtering by: date range, visitor name (partial-match text search), group type (dropdown), and assigned staff (dropdown). This directly satisfies FR-S-4. Provide a "New Booking" button (primary button style, #334155 background) in the top-right corner.
When creating or editing a booking, reuse the same validation logic as the public booking form, plus additionally allow staff to assign the booking to a specific staff member and gallery. Conflict detection must run immediately upon date/time/staff field change and display a visual indicator (amber warning badge) before the form is submitted (FR-S-6).
Logbook Interface. A dedicated view for recording visitor arrivals and departures (FR-S-2). Each logbook entry requires: linked booking reference (or "Walk-in" if unbooked), visitor name, group size, group type, arrival date, arrival time, departure time (may be entered later), gallery location, and the staff member recording the entry. The interface must be secure — only authenticated Staff and Curators may create or edit logbook entries. Walk-in registrations must be processable concurrently with standard arrivals without performance degradation (NFR Performance). Display incomplete logbook entries (e.g., arrival logged but no departure) with a distinct amber or red visual indicator and generate an in-system notification to the responsible staff member (FR-S-5).
Attendance Reports View. Provide real-time reports showing: total on-site visitors, breakdown by group size, and current location by gallery (FR-S-3). Reports must generate within 10 seconds. All figures are derived from live database queries — never from stored redundant counts (NFR Performance). An export button (labeled "Export CSV" and "Export PDF") must be visible at the top of the report. Export files must generate within 15 seconds (NFR Performance). Export buttons use the secondary button style.
Notification Panel. A persistent notification panel (accessible via a bell icon in the navigation) must surface: upcoming visits within the next 2 hours, incomplete logbook entries, and detected scheduling conflicts (FR-S-5, FR-S-6). Unread notifications display a red badge count on the bell icon using color #AC0000.

PART 5 — CURATOR INTERFACE (Oversight and Management)
Curators access a superset of the Staff interface, plus exclusive management functions. All staff views are available to curators. The curator-exclusive functions are described below.
Curator Dashboard. The curator's home view is an integrated overview dashboard showing: visitor activity summary (today's total bookings, on-site count), staff allocation map (which staff are assigned where), and an operational alerts panel for conflicts, incomplete logs, and high-load periods (FR-C-7). The dashboard must visually differentiate between normal state, warning state, and critical state using the following color coding: normal — teal #0f766e indicators; warning — amber rgba(245,158,11,1); critical — Heritage Red #AC0000. Use the same frosted-glass stat card pattern as the Staff Dashboard, scaled to 4–6 stat cards.
Staff Assignment Management. Curators can assign staff members or caretakers to specific galleries, exhibits, or time slots (FR-C-1). The assignment interface presents a visual calendar/grid showing galleries as rows and time slots as columns. Assigned staff appear as labeled chips within each cell. Conflicts (double-assigned staff or uncovered required slots) are shown with a red border and warning icon — visual indicators for conflicts or gaps are mandatory (FR-C-3). Curators can drag-and-drop staff assignments or use a form-based assignment panel.
Schedule Approval and Adjustment. Curators can review pending visitor booking requests and either approve or reject them, with a mandatory reason field for rejections (FR-C-2). Upon approval or rejection, the system automatically triggers a status notification to the visitor (linking to the notification system in the General Public section). Curators may also adjust approved schedules — any adjustment triggers re-validation for conflicts.
Role and Access Management. Curators can grant or restrict role-based access to staff members for specific operational functions (FR-C-6). The interface presents a list of staff members with toggles for each operational function. Every change is logged automatically with: the curator's name, the affected staff member, the function toggled, the new permission state, and the exact timestamp (NFR Security). This log is read-only and cannot be edited or deleted by any user.
Historical Reports and Trends. Curators can view historical attendance trends and staff activity reports (FR-C-4) using date-range selectors. Reports include: daily/weekly/monthly visitor volume charts, staff schedule adherence percentages, and entries-logged-per-staff metrics (FR-C-9). All charts use the portal color palette — #1e293b for primary data series, #0f766e for positive trends, #AC0000 for below-target or critical series. Export to CSV and PDF must be available for all curator-level reports (FR-C-8), generating within 15 seconds.
Recurring Schedules and Special Event Blocking. Curators can define recurring schedule templates (e.g., daily school group slot at 10:00 AM every weekday) and block out dates for special events or holidays (FR-C-10). Blocked dates must appear visually distinct in all calendar and booking views — use a diagonal stripe pattern or gray-out with a "Blocked — [Reason]" tooltip so both staff and the public see accurate slot availability.
Notification Management. Curators receive notifications for: high visitor load periods (defined as exceeding 80% of daily capacity), incomplete logbook entries older than 2 hours, and detected conflicts in staff assignments or visitor scheduling (FR-C-5). These notifications also appear in the persistent notification panel. High-load notifications must display a distinct urgency visual — Heritage Red #AC0000 header within the notification card.

PART 6 — SHARED UI COMPONENT SPECIFICATIONS
These components appear across two or more stakeholder interfaces and must be built as reusable, shared components.
Conflict Warning Component. A reusable amber/red banner or inline card that displays when a scheduling conflict is detected. Must include: conflict type (e.g., "Overlapping Booking," "Double-Assigned Staff," "Capacity Exceeded"), the conflicting records' reference numbers, and a suggested resolution action button. This appears in the booking form, the staff assignment grid, and the schedule approval view.
Notification Toast. A reusable overlay component triggered after every significant user action: booking submitted, logbook entry saved, assignment created, access permission changed, export completed. Position: top-right corner, auto-dismiss after 4 seconds, with a manual dismiss X. Green teal (#0f766e) for success, amber for warning, Heritage Red (#AC0000) for errors.
Search and Filter Bar. A reusable filter component accepting: date range (dual date picker), text search (partial match), and one or more dropdown selectors. Must apply filters on input change without requiring a separate "Apply" button press, for immediate feedback (NFR Usability). Used in Booking Management, Logbook, and Historical Reports views.
Export Button Group. A reusable two-button group: "Export CSV" (secondary style) and "Export PDF" (secondary style). Always positioned top-right of any report or list view. Must display a loading spinner while the file is generating and a success toast when the download is ready. Must complete within 15 seconds.
Role Guard Wrapper. A reusable component or HOC (Higher-Order Component) that wraps any route or UI section requiring role verification. If a user's session role does not match the required role, they are immediately redirected to their appropriate home view — never shown an error page that reveals the existence of the restricted page.
Privacy Notice Banner. A reusable, always-rendered banner component for the General Public booking form. Displays: what data is collected, how it is used, how it is stored, and that it is protected. Styled using Inter:Regular, weight 400, #64748b, line-height: 22.75px, within a light #f1f5f9 container with a #0f766e left border accent.

PART 7 — VALIDATION AND ERROR HANDLING (UNIVERSAL RULES)
Every input field must be validated at the point of entry — not on submit alone (NFR Reliability). Client-side validation gives immediate feedback; server-side validation runs before any database write. The following rules apply universally:
Required fields display a red border (#AC0000 or standard validation red) and a specific error message below the field when left empty on blur. Email fields validate format on blur and on submit. Numeric fields (group size, capacity) reject non-numeric characters on keystroke. Date fields reject past dates for new bookings. All text inputs strip leading/trailing whitespace before submission. All text inputs are sanitized server-side against SQL injection and malformed input (NFR Security).
Error messages must be clear and descriptive — for example: "Group size cannot exceed the remaining capacity of 12 for this time slot" rather than "Invalid input." (NFR Usability). Every validation error must identify exactly which field failed and why.
A consistent exception handling mechanism must exist across all service components: all errors are captured, logged server-side with a timestamp and the triggering user's session ID, and surfaced to the user as a friendly message that does not expose internal system details (NFR Maintainability, NFR Security).

PART 8 — DATA EXPORT SPECIFICATIONS
Both Staff and Curators can export data. The following constraints apply to all export functions.
CSV exports must be standard UTF-8 encoded, comma-delimited files openable on any operating system without proprietary software (NFR Portability). Column headers must match the display column names in the UI exactly. All date values must export in ISO 8601 format (YYYY-MM-DD). All time values must export in 24-hour HH:MM format.
PDF exports must preserve the visual hierarchy of the on-screen report: section headings in Inter:Bold / 700 weight, data rows in Inter:Regular / 400 weight, column headers in Inter:Semi_Bold / 600 weight. PDF files must be platform-independent and openable on any device.
Both export types must include a header block stating: report type, date range of data, date and time of export, and the name of the staff member or curator who requested the export.

PART 9 — AVAILABILITY AND GRACEFUL DEGRADATION RULES
The visitor-facing scheduling interface has the highest availability priority of all components in this module — public downtime directly affects museum access and reputation (NFR Availability). If the booking submission service is temporarily unavailable, the schedule browsing view must remain functional and display a message: "Booking submissions are temporarily unavailable. You may still browse available schedules. We apologize for the inconvenience and expect to restore full service shortly."
If the notification dispatch service is unavailable, booking submissions must still be accepted and stored. Notification delivery is retried automatically when the service is restored. Users are not shown an error about the notification — only about functionality that directly affects their interaction.
If the export service is unavailable, the report views must remain fully functional. The export buttons display: "Export is temporarily unavailable. Please try again in a few minutes."
The system must display informative notifications to users whenever any component is temporarily unavailable — users must never be left without context about why something is not working (NFR Availability).
